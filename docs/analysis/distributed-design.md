# 分布式 / 多实例扩展设计论证（一致性哈希跨节点）

> 状态：设计论证（未实测——单 GPU 环境无法给出可信的多节点数据，
> 见文末「为何只做论证」）。本文把单机三层方案推广到多节点，论证
> 现有构件（ShardedTieredStore、Scheduler/CrossNodeIndex、
> TransferEngineAdapter）在分布式形态下的组合方式与不变量保持。

## 1. 目标与非目标

**目标**：N 个推理实例（各自持有 HBM/DRAM/NVMe 三层）组成集群时，
(a) 前缀复用跨实例生效；(b) 节点增删只迁移 O(K/N) 的块；(c) 单机的
淘汰/预取/配额不变量在集群下仍成立。

**非目标**：跨节点强一致副本、分布式事务。KVCache 是**可重算的缓存**
——丢失的代价是重算而非错误，这是整个设计可以激进简化的根本前提。

## 2. 键空间划分：两级一致性哈希

单机 `ShardedTieredStore` 已把键空间 hash 划分到 16 个分片，分布式形态
是同一思想的第二级：

```text
请求前缀 → 会话锚（前 k 个块键的哈希） ── 一致性哈希环 ──→ 节点 n
                                                     │
块键 ──(节点内)── hash % 16 ──→ 分片 s ──→ TieredStorageManager
```

关键决策：**环上放置的单位是「会话锚」而非单个块键**。

- 若按块键独立哈希，同一请求的前缀块会被打散到所有节点——每次
  prefill 需要 N 路远程读，前缀复用退化为网络带宽竞赛。
- 按会话锚（前 k=4 个块键的组合哈希）放置，同一前缀树的块聚居在
  同一节点，前缀命中在节点内完成；跨节点只发生在路由决策（控制面，
  一次 hash 查询）而非数据面。
- 多轮会话的第 r 轮与第 r-1 轮前 k 块相同 ⇒ 会话锚相同 ⇒ 稳定路由到
  同一节点，天然复现单机的多轮复用收益（在线实测 TTFT p50 2.4×）。

虚拟节点：每物理节点 V=128 个虚拟点平滑负载（标准做法；V 越大方差
越小，128 时负载差异 <5%，参考 DynamoDB/Cassandra 经验值）。

## 3. 不变量保持论证

单机方案的核心不变量在集群下逐条检查：

| 不变量 | 单机来源 | 集群下如何保持 |
|---|---|---|
| 单层放置（块最多在一层） | TieredStorageManager | 键恒定映射到唯一节点+分片，节点内不变量原样成立；全局 = 各节点不变量合取（键空间不相交） |
| 容量上界 | 每层容量检查 | 每节点容量独立，无全局记账——一致性哈希保证键不跨节点重复放置 |
| S3-FIFO 淘汰语义 | fast 层策略 | 淘汰完全是节点内决策，无需跨节点协调 |
| 幽灵统计 | ghost 队列 | **本地化即可**：同一前缀树恒定路由到同一节点 ⇒ 该前缀的历史（幽灵命中）天然在同节点累积，跨节点共享幽灵无增益（与单机「分片间幽灵共享无增益」的负结果同构，见 REPORT.md） |
| 后继图预取 | PrefixPrefetcher | 后继边只在同一请求序列内产生，同一会话恒定同节点 ⇒ 图天然本地完整 |
| 多租户配额 | tenant_weights | 两级：集群级 `AllocateFairShare`（加权 max-min，已实现）分节点预算；节点内配额沿用单机实现 |

## 4. 路由与故障转移（复用既有控制面）

`src/scheduler/` 已实现所需控制面原语，分布式形态只是把输入换成
一致性哈希的输出：

- `CrossNodeIndex`：块键→持有节点集合（16 分片互斥量，原子过渡）。
  一致性哈希给出**主放置**，索引记录**实际持有**（含迁移中的旧节点、
  热点副本），二者分离使迁移/复制期间路由仍正确。
- `Route`：前缀感知路由——持有最多前缀块的可达节点优先（需求 4.1），
  这正是会话锚路由的运行时兜底：哈希环变更（扩容）后，旧节点仍持有
  块时优先复用旧节点，直至自然淘汰，**无需主动迁移数据**。
- `ChoosePlacementNode`：高水位避让（需求 4.4）处理倾斜负载——热前缀
  树导致某节点过载时，新会话放置避开之。
- `ResolveOnFailure`：持有者失联改选可达持有者，无则 `recompute=true`
  （需求 4.5）——缓存可重算前提下，故障转移即「重算 + 重新放置」，
  无需副本同步协议。

节点增删：一致性哈希保证仅 K/N 份额的会话锚重新映射；不迁移存量
数据（等其自然淘汰），新请求按新环放置——短暂命中率下降换取零迁移
复杂度，与 KVCache 的时效性（复用窗口短）匹配。

## 5. 数据面：TransferEngineAdapter 的位置

跨节点块搬运（热点副本、NVMe 层共享池化）走 `TransferEngineAdapter`
（对接 Mooncake TransferEngine 的 RDMA 批量传输）：控制面
`Route`/`CrossNodeIndex` 决定「从哪读」，数据面点对点搬运，不经过
调度器——与 Mooncake 本体的 P/D 分离架构同构，接口已在
`src/adapter/` 以 fake 双测验证读写往返。

## 6. vLLM 多实例接入路径

在线形态 = 每实例跑 `S3FIFOTieringOffloadingSpec`（三层）+ 前置
KV-aware 路由器：

1. 路由器对 prompt 分块取前 k 块哈希 → 会话锚 → 环上定位实例；
2. 实例内 vLLM 的 GPU 前缀缓存 / CPU / NVMe 三层照常工作（已实测）；
3. `fs` 次级层指向共享存储（如分布式 FS）时，实例间 NVMe 层自动
   池化——`FSSecondaryTier` 以文件名=块键寻址，天然支持多写者，
   这是零代码的跨实例共享形态。

## 7. 为何只做论证、不做实测（如实记档）

- 环境只有单张 RTX 5090：同机模拟多实例共享同一 PCIe/NVMe，
  测得的「跨节点」数字反映不了真实网络/NUMA 瓶颈，数据不可信；
- 多实例路由器 + 多 vLLM 进程的工程量 ≈ 在线预取方向的数倍，决赛
  窗口内性价比低于把单机三层证据做扎实（已完成：三层在线 2.2×、
  扫描干扰 p95 −15~19%）；
- 本设计的每个构件（分片、跨节点索引、公平配额、故障转移、传输
  适配）都已有实现 + 单测/属性测试守护（ctest 9/9），缺的只是
  多机环境下的端到端组装与测量。

**结论**：分布式扩展不需要新机制——单机方案的分片划分、控制面原语
与「缓存可重算」前提组合即得；一致性哈希以会话锚为放置单位是保住
前缀复用收益的关键决策。
